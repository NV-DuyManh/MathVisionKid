# MathVision Kids
## Phase 2.5 — System Contract & Shared Architecture Design

### 1. Executive Summary
This report defines the Phase 2.5 system contracts. It establishes a "Single Source of Truth" for the MathVision Kids architecture, resolving discrepancies between the Student Mobile and Teacher Web applications before Spring Boot or FastAPI development begins.

### 2. Existing Repository Reviewed
The current repository (`f:\MathVisionKid`) contains the Student Mobile app at the root and the Teacher Web app in a subdirectory (`teacher-web`). Both use internal `MockSubmissionService` and `MockTeacherService` respectively.

### 3. Existing Student Contract Audit
The Student app relies on `src/types/index.ts`. It correctly models specific errors (`ColumnValidation`), but uses a limited `SubmissionStatus` (e.g., `FEEDBACK_READY`, `CROP_REQUIRED`) that does not map directly to backend orchestration states. The confidence tracking is minimal and `Evidence` is implicitly tied to columns rather than being a standalone extensible model.

### 4. Existing Teacher Contract Audit
The Teacher Web app relies on `teacher-web/src/types/index.ts`. It tracks `Batch` status correctly but uses a completely divergent `SubmissionStatus` (`AI_CONFIDENT`, `OVERRIDDEN`). Confidence is stored as top-level `recognitionConfidence` and `diagnosisConfidence` properties instead of a unified `ConfidenceBundle`. Scores are assumed to be official instead of proposals.

### 5. Target Repository Architecture
The intended target structure separates apps and services:
```
MathVisionKid/
├── apps/ (student-mobile, teacher-web)
├── services/ (business-api, ai-service)
├── packages/ (shared-contracts)
└── contracts/ (openapi, examples)
```
*Note: To prevent breaking the current functional MVP apps, we did NOT move the existing Student or Teacher folders into `apps/` during this phase.*

### 6. Canonical Domain Model
Established strictly in `packages/shared-contracts/src/`:
- `Submission`, `Batch`, `Assignment`, `StudentFeedback`, `ValidationResult`.

### 7. Canonical Enums
- **SubmissionStatus**: `CREATED`, `IMAGE_UPLOADED`, `PROCESSING`, `NEEDS_CONFIRMATION`, `NEEDS_RETAKE`, `CROP_REQUIRED`, `FEEDBACK_READY`, `REVIEW_REQUIRED`, `OUT_OF_SCOPE`, `TEACHER_APPROVED`, `TEACHER_OVERRIDDEN`, `FAILED`.
- **Decision**: `VALID`, `INVALID`, `UNCERTAIN`.
- **ErrorType**, **ImageQualityIssue**, **ReviewReason**.

### 8. Submission State Machine
- `CREATED` → `IMAGE_UPLOADED` → `PROCESSING`
- `PROCESSING` → `FEEDBACK_READY` | `NEEDS_CONFIRMATION` | `REVIEW_REQUIRED` | `OUT_OF_SCOPE` | `NEEDS_RETAKE`
- `FEEDBACK_READY` | `REVIEW_REQUIRED` → `TEACHER_APPROVED` | `TEACHER_OVERRIDDEN`

### 9. Student API Contract
- `POST /api/v1/student/submissions`
- `GET /api/v1/student/submissions/{submissionId}`
- `POST /api/v1/student/submissions/{submissionId}/confirm-token`

### 10. Teacher API Contract
- `POST /api/v1/teacher/batches`
- `GET /api/v1/teacher/batches/{batchId}`
- `GET /api/v1/teacher/batches/{batchId}/review`
- `POST /api/v1/teacher/submissions/{submissionId}/approve`
- `POST /api/v1/teacher/submissions/{submissionId}/override`

### 11. Authentication Contract
Defined structurally as returning a standard `Bearer` token (`LoginResponse`). Implementation deferred.

### 12. Batch Processing Contract
Asynchronous polling pattern. `BatchStatus` transitions from `UPLOADING` → `PROCESSING` → `COMPLETED`/`REVIEW_REQUIRED`.

### 13. Evidence Contract
Canonical `Evidence` requires `evidenceId`, `type`, `placeValue`, `ruleId`, `expectedRelation`, `observedRelation`, `confidence`, and normalized `boundingBox` `[0.0, 1.0]`.

### 14. Confidence Contract
Consolidated into `ConfidenceBundle` (`recognition`, `structure`, `diagnosis`).

### 15. Grade Proposal / Approval Contract
Scores generated by AI are wrapped in a `GradeProposal` with `isOfficial: false`. Only a `TeacherDecision` can finalize the score.

### 16. Audit Contract
(Deferred structure for future database auditing of decisions).

### 17. Error Response Standard
Defined `ApiErrorResponse` wrapping an `error` object with `code`, `message`, `requestId`, and `details`.

### 18. FastAPI Internal Contract
Defined in `contracts/ai/ai-contract.md`. Takes `imageReference` and `allowedOperations`, returns canonical validation/evidence payload.

### 19. Spring Boot Responsibility
Orchestration, DB persistence, User auth, File storage references, Audit logging, Client-facing REST API.

### 20. FastAPI Responsibility
Image OCR, structural parsing, math arithmetic validation, and rule generation.

### 21. Client Responsibility
Capture, Display, User Confirmation, and specific workflow navigation. Clients do NOT calculate correctness.
